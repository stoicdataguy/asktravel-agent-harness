# AskTravel (travel-agent) — project instructions

Lightweight LangChain ReAct agent for planning travel itineraries, served by FastAPI
behind an off-the-shelf chat UI. Living document: append new conventions as sections below.

## Stack
- Python 3.12, managed with **uv** only (never pip/poetry/conda). `uv add <pkg>`, `uv run <cmd>`.
- Backend: **FastAPI** + uvicorn. Agent: **LangChain v1** `create_agent` (LangGraph under the hood).
- LLM calls go through **OpenRouter** via `ChatOpenAI(base_url=OPENROUTER_BASE_URL)`. No direct provider SDKs.
- Frontend: **none of our own.** We expose an OpenAI-compatible API (`/v1/models`, `/v1/chat/completions`)
  and use Open WebUI (docker-compose) as the chat client. Don't build UI code. It's branded **AskTravel**
  via `WEBUI_NAME` + `branding/` assets (generated by `scripts/make_branding.py`); keep the
  "(Open WebUI)" attribution Open WebUI adds. The model id stays `travel-agent`; its display name is
  `AGENT_DISPLAY_NAME` (AskTravel).

## Commands
- Infra: `docker compose up -d` → Postgres :5433, Open WebUI http://localhost:3000, Langfuse http://localhost:3001
  (Open WebUI's tables live in our Postgres, schema `open_webui`; an old SQLite install is copied over
  once with `scripts/migrate_owui_to_postgres.py`, see its docstring)
- Chat deletion e2e: `uv run python scripts/e2e_chat_deletion.py [--api …]` — a chat deleted in Open WebUI
  loses its thread and chat-index entry (needs an API from current code)
  (Langfuse stack lives in `docker/langfuse.compose.yml`; local dev secrets only)
- Run API: `uv run travel-agent` (or `uv run uvicorn travel_agent.api.app:app --reload`)
- Guidebooks: `uv run travel-agent-ingest [--force]` converts `reference/*.pdf` → `data/guidebooks/*.md`
- Demo GIF: `uv run python scripts/record_demo.py` → `docs/demo.gif` (needs the full stack running)
- Skill triggering eval (real LLM): `uv run python scripts/eval_skills.py` — run after editing any skill description
- Memory eval (real LLM + Postgres, no API needed): `uv run python scripts/eval_memory.py [--quick] [--only <case>] [--json out.json]`
  — pass rate per case (each run 3×) and input/cached tokens per model call; the memory plan's
  §8 cases. Full run ~15 min, `--quick` a few. Some cases fail until their phase lands; compare
  against the baseline in the plan's §8.
- Context-window replay: `uv run python scripts/context_window_trace.py [--thread <id>]` → JSON (token counts and
  tool names only) for the "Context window" tab of `docs/architecture.html`; regenerate it after changing
  compaction or the prompt.
- Inspect state (SQL + decoded threads): `uv run jupyter lab` → `notebooks/inspect_state.ipynb`.
  Commit notebooks without outputs (they contain user data).
- Tests: `uv run pytest` · Lint/format: `uv run ruff check --fix . && uv run ruff format .`

## Layout
- `src/travel_agent/` — package (src layout). `config.py` holds all settings (pydantic-settings, `.env`).
- `src/travel_agent/api/` — FastAPI app and OpenAI-compatible routes.
- `src/travel_agent/agent/` — `build_agent()` (create_agent + middleware that injects skills and saved memories), prompts;
  `compaction.py` = turn compaction (earlier turns sent without tool results; request-only).
- `src/travel_agent/memory.py` — Postgres checkpointer + store on one connection pool.
- `src/travel_agent/observability.py` — Langfuse callback + `run_config()`. Tracing is Langfuse only (no LangSmith).
- `src/travel_agent/tools/` — agent tools; `guidebooks.py` = keyword search / page reads over extracted guidebooks.
- `src/travel_agent/context.py` — `UserContext` (runtime context: `user_id`).
- `src/travel_agent/agent/schemas.py` — `Itinerary` schema + `render_itinerary()` markdown.
- `src/travel_agent/tools/itinerary.py` — `present_itinerary` (structured plan → store + chat).
- `src/travel_agent/tools/flights.py` — `search_flights` (Google Flights via fast-flights; sync lib run in a thread).
- `src/travel_agent/tools/hotels.py` — `search_hotels` (Playwright on Google Hotels; `parse_card` is pure and unit-tested).
- `src/travel_agent/tools/trips.py` — trip memory (`Trip`, `save_trip_details`, `get_trip`, `delete_trip`,
  `match_trip`, `trip_status`, startup id migration + backfill).
- `src/travel_agent/user_data.py` — view / export / delete-all of one user's data (`/api/memory`).
- `src/travel_agent/tools/memory.py` — long-term memory tools (`save_memory`, `delete_memory`) + loaders.
- `src/travel_agent/tools/conversations.py` — episodic recall: chat index (`index_chat` middleware,
  startup backfill) + `recall_conversations` keyword search over the user's other threads.
- `src/travel_agent/skills/` — skill playbooks (`<name>.md` with name/description frontmatter) + `load_skill` tool.
- `src/travel_agent/kb/` — guidebook ingestion (PDF → markdown with `[p. N]` markers + TOC headings).
- See `docs/PLAN.md` for the target architecture and milestones, and `docs/architecture.html` for the
  visual architecture + state-persistence pages (update it when components or storage change).

## Conventions
- Settings only via `travel_agent.config.get_settings()`; never read `os.environ` directly.
- Structured data = Pydantic v2 models. Structured agent output goes through a tool whose argument is the
  model (see `present_itinerary`), not `create_agent(response_format=...)`, which forces a tool call on every
  turn. Tools that show something to the user return `(content, markdown)` with
  `response_format="content_and_artifact"`; the API streams string artifacts into the chat.
- Tools: plain typed Python functions with docstrings (docstring = tool description the LLM sees).
  Tools must return compact, LLM-friendly output (trim large payloads) and never raise into the agent
  loop — return an error string instead.
- Memory is **Postgres only** (no SQLite/in-memory outside tests). Thread memory via checkpointer keyed
  `thread_id = "<user_email>:<chat_id>"`; cross-thread facts via `Store` namespaced
  `(<email with "." → "%2E">, "memories")` (store labels can't contain dots); use
  `memory.user_namespace(user_id, kind)` rather than building namespaces by hand.
- Trip ids are opaque (`trip-xxxxxx`, `new_trip_id()`) and never derived from the destination or
  changed. Writes without a known id go through `match_trip` (destination words + compatible dates,
  upcoming trips only, no merge when ambiguous). Old ids live on in `Trip.aliases`; look trips up
  with `find_trip`, not `store.aget`. Time-relative facts (`trip_status`) are computed when the
  prompt is built, never stored.
- Any new per-user data must live in a store namespace from `memory.user_namespace(user_id, kind)`
  or a thread keyed `<email>:…`: `user_data` finds both generically, so view, export and
  delete-all cover it without changes. Anything stored elsewhere needs its own deletion path.
- Memory consolidation (M5, `consolidation.py`) runs in the API's background loop once a user's
  chats are idle (`CONSOLIDATION_IDLE_MINUTES`). Its model only sees the user's own messages and
  saved facts, never tool results; code applies only changes whose evidence quote is really there,
  never edits `sensitive` facts, and logs each change to `(email, "memory_log")`. The chat index
  entry is merged, not overwritten: it carries `turns` / `consolidated_turns`.
- Long-term memory has two kinds: profile facts (`save_memory`, lasting preferences) and trips
  (`save_trip_details`, per-trip details). Both are injected into the prompt by the middleware;
  `present_itinerary` always files the plan under a trip. Store values must be JSON-safe
  (`model_dump(mode="json")` for models with dates).
- Profile facts: keys in `tools/memory.LIST_KEYS` (likes, dislikes, interests) are lists: a save
  adds de-duplicated items (`{"items": [...], "value": "a; b"}`), never rewrites. Other keys
  overwrite, and the tool result shows the old value. Every fact carries `source` (thread id),
  `confirmed_at` and `updated_at`. Read facts via `value`; reshape old rows in a startup migration
  (`migrate_memories`) rather than in readers.
- Store/checkpointer are async Postgres: anything touching them (tools, middleware) must be
  `async def` and use `aput`/`asearch`/…; sync calls fail inside the event loop.
- Identity: `user_id` = `X-OpenWebUI-User-Email` header (lowercased), passed as `UserContext` runtime
  context. Tools read it from `runtime.context.user_id`; never take user_id as an LLM-visible argument.
- Context budget: never rewrite the saved thread to shrink context (`SummarizationMiddleware` does,
  and breaks `thread_sync` rewind). Shrink only the request, in `wrap_model_call` middleware, and
  keep the result deterministic per turn so the prompt prefix stays cacheable.
- The checkpointer owns history. Before each run `api/thread_sync.plan_run` compares the UI
  transcript's user messages with the thread: append the newest message when they agree, seed an
  empty (forked) thread from the transcript, or rewind/replace on regenerate and edit. Clients must
  send the full transcript, as OpenAI-style clients do.
- After changing memory, prompts or tools, run `uv run python scripts/e2e_memory.py` (cross-chat memory)
  and the `eval_memory.py` cases the change can affect, and report pass rates against the plan's §8.
- **Live test budget (they're slow, ~20 model calls/min):** while coding, unit tests only. Before a
  PR, only the eval cases the change can affect, once each (`--only a,b --runs 1`), plus the one
  e2e script that covers the feature. The full 3-run suite (~15 min) only when a phase targets a
  number in the plan (e.g. M2 tokens, M3 recall). Run live suites in the background and keep working.
- A worktree can test against its own server: run it on another port and pass `--api` to
  `e2e_memory.py` (other e2e scripts still assume :8000).
- Token usage per model call (input, cache read, cache write) is on every Langfuse generation;
  OpenRouter does cache `gpt-6-luna` prompts, so keep the start of the prompt stable.
- After changing flight or hotel search, run `uv run python scripts/e2e_flights.py` / `e2e_hotels.py`
  (both check quoted prices against a live Google lookup). If Google changes its markup, update
  the selectors in `tools/hotels.py` and the captured card texts in `tests/test_hotels.py`.
- OpenRouter limits new accounts to 20 requests/min on gpt-6-luna. Model calls retry 429s with
  backoff (`LLM_MAX_RETRIES`), so suites can run back to back; they just slow down near the limit.
  Set `LLM_REQUESTS_PER_MINUTE` (e.g. 18) to pace calls instead of retrying.
- Errors inside an agent run must never break the SSE stream: `openai_compat` turns them into a
  readable message (`error_message`) followed by `[DONE]`.
- After changing anything in the request path, run the browser test
  `uv run python scripts/e2e_branching.py` (full stack running).
- Flights: `fast-flights`. Hotels and web pages: Playwright scraping. No paid search APIs.
- `reference/` (raw PDFs) and `data/guidebooks/*.md` are copyrighted material: never commit them.
- Every agent invocation (incl. future subagents) uses `observability.run_config(user_id, thread_id)`
  so traces get tracing callbacks plus session/user metadata (`langfuse_session_id`, `langfuse_user_id`).
- Langfuse v4 runs in events-only mode: query traces via `/api/public/v2/observations`, not `/traces`.
- Streaming shows agent progress (`api/progress.py`): each tool call as `🔧 name(args)` plus an
  outcome summarised in code (`summarize()`, counts and prices only, never guidebook text), sent
  as `reasoning_content` so Open WebUI shows it in a collapsible block above the answer and never
  resends it. Keep tool names and args human-readable. Progress never goes in `content` unless
  `PROGRESS_STYLE=inline`. A new tool needs a `summarize()` case (or it shows its first line).
- A tool that takes more than a few seconds reports its steps with `tools/report.py`:
  `report(runtime, "dates set…")` (add `runtime: ToolRuntime = None`, hidden from the model).
  It shows as `⋯ tool: text` under the call, logs the step's timing, and does nothing outside a
  stream.
- Progress e2e: `uv run python scripts/e2e_progress.py` (browser; checks progress shows fast, the
  answer stays clean, every tool call has an outcome). Run it after changing the request path.
- Deleting a chat in Open WebUI is followed through by a trigger on `open_webui.chat` (installed by
  the API, `chat_deletions.py`) plus the API's sync loop. Upgrading Open WebUI can change its tables:
  rerun `e2e_chat_deletion.py` after an Open WebUI upgrade.
- Open WebUI runs with `ENABLE_PERSISTENT_CONFIG=false`: docker-compose.yml is the source of truth for
  its settings (it otherwise disables signup in its DB after the first account). Admin-panel changes
  don't survive restarts; put them in compose instead.
- Skills: the description decides when the agent loads it, so write it as "Use when …" with
  concrete trigger phrases (and when NOT to use it). Filename must equal the `name`. Add a case to
  `scripts/eval_skills.py` for every new skill.
- Async first in the API layer (`ainvoke` / `astream`).
- Secrets live in `.env` (gitignored). Keep `.env.example` in sync when adding settings.

## Workflow
- Small commits; run ruff + pytest before committing.
- Tests must not hit real LLMs or the network — use fake chat models / mocks. `tests/conftest.py`
  forces tracing off. If a test needs tracing on, use `FakeListChatModel`: tracer serialization
  consumes `GenericFakeChatModel`'s message iterator (seen with LangChain tracers). For agents with tools use `tests.fakes.FakeToolModel`
  (script tool calls as `AIMessage(tool_calls=...)`, with `disable_streaming=True`).

## Feature-driven development
**Every feature and every bug fix is built on a branch and lands through a pull request.** No
exceptions for small fixes or docs.

How git behaves here (GitHub ruleset "Protect main" on the default branch):
- `git push origin main` is **rejected** by GitHub. Commit on a branch, push the branch, open a PR.
- Force pushes (`--force`, rewritten history) to `main` are rejected, and `main` can't be deleted.
- Merging is done through the PR (`gh pr merge`), never by pushing a local merge to `main`.
- Locally, `main` only moves by `git pull` after a PR merges. If you committed on `main` by
  mistake, move the commit to a new branch (`git switch -c feat/<slug>`) and push that.
- No CI yet, so the PR itself is the gate: run the tests below before opening it.

1. **Issue first.** File every feature or bug as a GitHub issue (`gh issue create`). Features
   state the problem, acceptance criteria written as checks an end-to-end test can make, and what
   is out of scope. Bugs give steps to reproduce, expected and actual behaviour.
2. **Plan when it's big.** Work spanning several PRs or changing architecture gets a plan in
   `docs/plans/<name>.md`, linked from `docs/PLAN.md`, before any code.
3. **One feature, one branch, one PR.** Branch from an up-to-date `main` as `feat/<slug>`,
   `fix/<slug>` or `docs/<slug>`. Don't stack PRs on each other's branches: deleting the base
   branch on merge auto-closes the stacked PR (#10).
4. **Test end to end.** Unit tests stay offline (see Workflow). A user-visible feature also gets
   a browser or live suite, `scripts/e2e_<feature>.py`, that checks the acceptance criteria
   against the full stack and the real model. Before opening the PR, run it plus the regression
   suites the change can affect (the e2e scripts named under Conventions, `eval_skills.py`).
5. **Docs in the same PR.** Update this file for new conventions, `docs/PLAN.md` status,
   `docs/architecture.html` when components or storage change, and `.env.example` for new settings.
6. **Open the PR.** Title = the user-visible outcome. Body: summary, `Closes #N` / `Fixes #N`, and
   how it was tested with the suite results (pass counts). Commit and PR attribution lines as the
   harness specifies.
7. **Merge only with explicit approval, one PR at a time.** The user approves each merge;
   approval of one PR doesn't carry to the next. Squash-merge (`gh pr merge N --squash`), then
   `git checkout main && git pull`. To bring an open branch up to date, merge `main` into it;
   never rebase or force-push a pushed branch.

### Tracking work in GitHub Projects
All work is tracked on the **AskTravel** project: https://github.com/users/stoicdataguy/projects/1
(linked to the repo). Every issue lives on the board; the board is where sprints and progress are
read, so keep it in step with the work.
- **Fields:** Status (Todo / In Progress / Done), Sprint (2-week iterations), Story Points,
  Phase (MVP, Feedback, Memory, Production, Agent), Priority (P0–P2).
- **New issue → add it to the board** with Status, Phase, Priority and Story Points (issues are
  not auto-added): `gh project item-add 1 --owner stoicdataguy --url <issue url>`, then
  `gh project item-edit` per field. Field and option ids: `gh project field-list 1 --owner stoicdataguy --format json`.
- **Starting work → Status = In Progress** on the issue's item (find it with
  `gh project item-list 1 --owner stoicdataguy --format json`).
- **Done is automatic:** a merged PR with `Closes #N` closes the issue, and the project's
  built-in workflow moves it to Done. Check the board after merging.
- **Scope changes** (split, deferred, new bug found mid-feature) become new issues on the board,
  not unchecked TODOs in a PR.
- `gh` needs the `project` scope: `gh auth refresh -s project` if a project command says it's missing.
