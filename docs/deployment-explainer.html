Putting AskTravel in the cloud, explained

A companion to docs/plans/deployment.md. The plan says what to do; this page explains the words in it and why each choice was made. It's written for someone who knows the fundamentals but hasn't run anything in production. Revised for EC2 with AWS-native services (#98), so the beta also teaches real AWS.

1 server

An EC2 t4g.small (2 GB, arm64) in a VPC, running the same Docker Compose stack you run on your laptop

~$21 / month

Hosting: $12.26 server + $3.65 public IP + disk, DNS, snapshots. ~$33 if it needs 4 GB. LLM usage is separate

0 SSH, 0 keys

The security group opens only 80 and 443. No SSH port, no key pair, and no AWS access keys anywhere: IAM roles and SSM instead

1 click

To ship: merge a PR, approve the deploy, and the pipeline does the rest, rolling back if a health check fails

Follow one chat message

What happens between a beta user pressing Enter and the answer streaming back. Each step names the concept it relies on.

  1. The browser looks up asktravel.<domain>Route 53 answers with the server's Elastic IP (an A record). It's cached for a while (the record's TTL), which is why DNS changes take minutes to show.
  2. It opens an encrypted connection on port 443The security group lets 443 through. Caddy presents a TLS certificate from Let's Encrypt proving it really is your domain, so the password and chat can't be read on the way.
  3. Caddy forwards the request to Open WebUICaddy is a reverse proxy: the only thing listening publicly. It hands the request to the open-webui container by name, over the private Docker network.
  4. Open WebUI checks who you areYour session cookie (signed with WEBUI_SECRET_KEY) identifies your account. It then calls the agent API like any OpenAI-compatible model, adding your email as a header and the shared bearer token.
  5. The agent API runs a turnIt rejects calls without the token (#27), loads the thread and your memories from Postgres, and runs the agent loop. It calls OpenRouter for each model step and Google for flights and hotels, all outbound HTTPS.
  6. Traces go to LangSmithEach model call and tool call is sent in the background, so you can see later what happened and what it cost.
  7. The answer streams back the same wayServer-sent events flow API → Open WebUI → Caddy → browser for 30–90 s. Every hop must allow long, unbuffered responses, one reason the plan uses Caddy, which does.

Follow one commit to production

CI (continuous integration) checks every change automatically. CD (continuous deployment) ships every change that passes. Here's the path of a prompt tweak.

1 · BranchCommit on feat/… on your laptop, push it
2 · Pull requestCI runs ruff and pytest on a fresh GitHub machine (a runner)
3 · MergeOnly if CI is green (a required check). main moves
4 · BuildTests again, then an arm64 Docker image tagged with the commit SHA → ECR
5 · ApproveThe job waits in the production environment until you click
6 · ConnectThe job trades a GitHub OIDC token for a short-lived AWS role, then asks SSM Run Command to run the deploy. No SSH
7 · Deploydeploy.sh <sha>: backup, pull, restart, health check
8 · Live or rolled backHealthy → done. Unhealthy → previous image restored, run turns red

Why tag images by commit SHA and not latest: a SHA always means exactly one build. A rollback is "deploy the SHA that worked", and you can always tell what's running.

The decisions, and what each one gives up

Every architecture choice trades something away. Open a decision to see the alternatives, the cost of choosing it, and the signal that it's time to revisit.

D-1One server, or managed containers (ECS, RDS, load balancer)?One server with Docker Compose

Why

It's the stack you already run, so the new things to learn are the cloud parts, not a new runtime. The managed design (Fargate + RDS + load balancer) costs ~$110–150 a month; the load balancer alone exceeds the budget.

Given up

High availability: if the server dies, AskTravel is down until you restore it. Deploys cause 10–30 s of downtime. No automatic scaling.

Revisit when

Users pay, you promise uptime, or one server can't keep up. The skills carry over: images, DNS, TLS, secrets, CI/CD.

D-2Which kind of server, from whom?EC2 t4g.small (arm64), us-east-1

Why

It teaches the AWS concepts everything else builds on: VPC, subnets, security groups, EBS, Elastic IPs and IAM roles. With a role, the server needs no AWS keys. arm64 (Graviton) is ~20% cheaper than x86. A US region keeps Google's results as they are on your laptop.

Given up

~$8 a month more than Lightsail (whose price includes the IP and disk), more setup, and more ways to make a costly mistake: NAT gateways, idle IPs, unlimited CPU credits. Images must be built for arm64. Memory is still tight at 2 GB.

Revisit when

D0 shows memory pressure (t4g.medium, 4 GB) or an arm64 problem (t3.small). After a month: capture it as infrastructure as code. If cost matters more than learning AWS, Lightsail 2 GB ($12) is the simpler fallback.

D-3Where do traces go?LangSmith, free plan

Why

Self-hosted Langfuse was six containers using ~4 GB (measured locally; ClickHouse alone 2.5 GB), more than the rest of AskTravel combined. LangSmith (since #87) is cloud only, native to LangChain, and its free plan gives 5k traces a month: one trace per chat turn.

Given up

Your traces (which contain users' messages) live with a third party, and you see only the last 14 days. Dev and prod share the 5k, so use a separate prod project and keep evals untraced.

Revisit when

Usage nears the limit: sample traces, or pay.

D-4Where do builds run and images live?GitHub Actions (arm64 runner) + ECR

Why

Actions and its arm64 runners are free for public repos and build the image natively. ECR is private and uses IAM: the workflow pushes through its OIDC role and the server pulls through its instance role, so no registry password exists anywhere.

Given up

A few cents a month of storage (a lifecycle policy keeps the last 15 images), and some IAM setup that GHCR wouldn't need.

Revisit when

Rarely. ECR is also what ECS uses, so it carries over when you outgrow one server.

D-5How does CI reach the server?OIDC role + SSM Run Command, after your approval

Why

No SSH at all: the SSM agent on the server connects out to AWS and runs the deploy command it's given. GitHub gets temporary AWS credentials through OIDC, so it stores no keys. CloudTrail records every deploy. Rollback is a re-run.

Given up

More IAM to understand up front: an identity provider, a role with a trust policy, and permissions scoped to one instance tag.

Not chosen

Tailscale + SSH (the earlier plan: simpler, less AWS). SSH open to the world. An auto-updater on the server (no approval, no visibility). CodeDeploy (more services for one server).

D-6Who terminates HTTPS?Caddy, on the server

Why

Automatic Let's Encrypt certificates and renewals from a tiny config file, streaming without buffering, about 30 MB of memory.

Given up

One more container to keep updated (pinned, like the others).

Not chosen

Nginx + certbot (more to learn at once). An Application Load Balancer with a free ACM certificate (~$16–20 a month, more than the server). It's the first thing to add with a second server.

D-7Do we need a staging environment?Not yet

Why

A second server doubles the cost. Running the production compose file on your laptop (D3) catches packaging problems, and the approval step is a last look.

Given up

Testing on a real cloud server before users see a change. Problems specific to the server (memory, Google blocking) show up in prod.

Revisit when

More users or more contributors: with infrastructure as code, a t4g.micro staging instance and a staging environment in the same workflow.

D-8Where do secrets live?SSM Parameter Store (SecureString)

Why

Encrypted with KMS, free on the standard tier, and readable only by the instance role and your admin login. deploy.sh writes them into .env just before starting the containers. Rotating a secret is "change the parameter, redeploy".

Given up

No automatic rotation, and the values still sit in a file on the server while it runs.

Not chosen

Secrets Manager ($0.40 per secret a month; its rotation is for databases like RDS). A hand-copied .env (the earlier plan: no audit trail).

Four things that can stop the beta

None of them is solved by infrastructure. Decide each one in D0, before you spend time on the rest.

Guidebook copyrightServing Lonely Planet excerpts to 100 people is distribution. Get permission, switch the guidebook tools off, or use openly licensed sources such as Wikivoyage.
Open WebUI's branding licenceCustom logos are allowed for up to 50 users in 30 days. Cap the beta at 50, or use Open WebUI's own logo beyond that.
Google blocks cloud IPsFlights and hotels scrape Google, which often challenges data-centre traffic. D0 tests it from a real AWS server for pennies.
The model's rate limit~20 calls a minute ÷ ~3.7 calls per turn ≈ 5 turns a minute for everyone, about 10 people chatting at once. Raise it, add a fallback (#51), or invite in waves.

Things that surprise people the first time

A stopped EC2 instance still costs moneyThe instance stops billing, but its disk, snapshots and public IP don't. An Elastic IP that isn't attached to anything bills too.
Every public IPv4 address costs $3.65 a monthSince 2024, including Elastic IPs. Keep exactly one, and release spike IPs the same day.
t4g "unlimited" CPU bills extrat4g instances launch in unlimited credit mode, which charges for sustained bursts. Choose standard: a busy hour then slows down instead of costing more.
The free plan closes the accountA free-plan account is closed after 6 months or when its credits run out. Upgrade to the paid plan before the beta.
Untested backups aren't backupsThe restore drill (D6) is the only proof. Time it: that's how long a disaster takes to recover from.
Logs fill disksDocker keeps container logs forever by default. The prod compose caps them at 3 × 10 MB per service.
"latest" isn't a versionPin Open WebUI and Postgres to exact versions. Upgrades are deliberate PRs, because Open WebUI's upgrades can change the tables our deletion trigger watches.
Secrets leak through images and gitAnything copied into an image is readable by anyone who pulls it. Keep .env, data/ and reference/ in .dockerignore.
Port 22 open = constant attacksBots try SSH passwords on every public IP within minutes. Not opening it at all (no key pair, Session Manager) beats defending it.
Access keys leak; roles don'tA key in a file or a GitHub secret works for anyone who copies it, forever. Roles hand out credentials that expire within hours, so this plan has none to leak.
NAT gateways and load balancers bill by the hourThe classic surprise AWS bill. This plan uses neither, and the budget alert catches anything you add by mistake.
