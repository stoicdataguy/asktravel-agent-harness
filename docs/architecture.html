System overview

How a chat message becomes a trip plan

AskTravel is a travel-planning agent. Open WebUI, branded as AskTravel, is the only frontend. It talks to our FastAPI service as if it were an OpenAI model; behind that API, a LangChain agent researches with tools and keeps its state in Postgres.

Agent runtime

langchain create_agent · ReAct loop
model→tool calls→tools→model…final answer

Before every model call, a middleware rebuilds the system prompt: base instructions + the skills index + this user's saved facts and trips. In the background, once a user's chats have been idle for 10 minutes, one model call reviews their saved facts and applies guarded fixes (memory consolidation). A second middleware compacts earlier turns of the chat for the model: their tool results are dropped (skills and the latest itinerary stay), while the saved thread keeps everything. Every tool and skill is described on the Tools & skills tab.

One request, end to end

  1. The user sends a message in Open WebUI.Open WebUI posts the whole transcript plus the user's email and chat id.
  2. The API resolves who and where.user_id = email, thread_id = email:chat_id. If the transcript matches the saved thread, only the newest message goes on; if the chat was forked, regenerated or edited, the thread is seeded or rewound to match first.
  3. The agent loads the thread.The checkpointer restores this chat's message history from Postgres.
  4. The middleware builds the prompt.Base instructions, the skills list and the user's saved facts from the store. Earlier turns are sent compacted: question, answer and a note of the tools used.
  5. The model works through tools.It may load a skill, search the guidebooks, save a fact or present an itinerary. Each step is checkpointed.
  6. The API streams back.Tokens, a 🔧 status line per tool call, and any rendered itinerary, as OpenAI-style SSE chunks.
  7. Everything is traced.Langfuse records the turn under the chat's session and the user's email.

One turn that saves a memory

The user writes "I'm vegetarian" in an existing chat. Amber steps touch short-term memory, violet steps touch long-term memory, blue steps are the request and model calls.

The memory list is re-read before every model call, so a fact saved in step 7 is re-read in step 9 and already in the prompt for step 10. Checkpoints are written after each step, not only at the end of the turn.

When the chat branches

Open WebUI lets people fork a chat, regenerate an answer or edit an earlier message. Before every turn the API compares the user messages in the transcript Open WebUI sends with the ones in the saved thread, and keeps the thread on the branch the person is looking at.

ActionWhenWhat happens to the thread
AppendTranscript and thread agree (the normal case)Only the new message is added
SeedForked chat: new chat id, so an empty thread, but the transcript has earlier turnsThe earlier turns are copied in from the transcript (tool status lines stripped), then the new message
RewindRegenerate, or an edited later messageThe run starts from the last finished turn that matches the transcript (LangGraph checkpoint time travel). The old branch stays in history
ReplaceNo earlier turn matches, e.g. the first message was editedThe thread's messages are replaced with the transcript

Only user messages are compared: Open WebUI's copy of each answer includes tool status lines and rendered itineraries, so it never matches the model's own messages exactly. Covered by tests/test_thread_sync.py and the browser test scripts/e2e_branching.py.

Every checkpoint is a full restorable snapshot, which is what makes resuming, and later forking a thread for edits, possible. Old checkpoints are never pruned today.

Gaps to know about

  • TrustIdentity comes from a header.The agent API trusts X-OpenWebUI-User-Email, and /api/memory can read or delete a user's data, so a forged header reaches someone else's memory. Fine on a laptop; before any deployment it needs a bearer token and a private network (#27).
  • RetentionNothing expires.Checkpoints are never pruned and memories have no TTL (the store already supports ttl_minutes; planned as M6). Users can delete everything themselves with DELETE /api/memory, and deleting a chat in Open WebUI now deletes its thread. Its saved itinerary stays with the trip on purpose.
  • KnowledgeThe knowledge base is keyword search over 2016 guidebooks.Only 7 destinations, editions years out of date (the agent flags prices and hours), and no search by meaning: a question worded differently from the book can miss. Future state: a trusted, indexed knowledge base (above).
  • QualityResearch answers aren't measured.Memory has an eval suite (22/22) but guidebook answers don't: nothing checks that facts are right or that page citations point at the right page. Needed before changing retrieval.
  • CapacityThe model provider rate-limits at about 20 requests a minute.Busy minutes trigger 429s, and retries add 30–50 s waits. Not yet known whether the limit is OpenRouter's or the upstream provider's (#51).
  • CouplingChat deletion depends on Open WebUI's tables.A trigger on open_webui.chat queues deletions. An Open WebUI upgrade that changes that table would silently stop it; rerun e2e_chat_deletion.py after upgrading.
  • ScaleMemory is capped, not searched.Up to 50 facts are injected every call. Past chats are found by keyword search. Beyond that, switch facts and chats to semantic search on the store.

Tokens written to the prompt cache on each call

Everything else in the call was read from cache at about a tenth of the price. A request is served from cache only if it extends an earlier one exactly.

Within a turn: append onlyEach step adds the model's tool calls and their results to the end. The window grows (turn 5: 7k → 26k across 7 calls while the agent reads guidebook pages), but everything before the new results is read from cache.
At a new turn: compact onceThe previous turn's tool results are dropped, leaving its question, answer and a one-line note. The window falls back (26k → 11k at turn 6) and the new request still extends one the cache holds.
When the cache missesTurns 13–15 each present a new itinerary. Compaction keeps only the latest plan, so the earlier one leaves the middle of the window and ~7k tokens are rewritten. A new day or a mid-turn memory save does the same (#55).

Current MVP

What the agent can do

Tools are actions the agent can take: Python functions it calls with arguments. Skills are instructions: markdown playbooks it reads before tackling a kind of request. Skills tell the agent which tools to use and how.

Tools

Typed functions the model calls

The model sees each tool's name, arguments and docstring. Every call appears in the chat as a 🔧 name(args) line and in Langfuse as its own step. Tools never raise into the loop; they return an error message the model can act on.

Skills

Playbooks loaded on demand

Only each skill's name and "Use when…" description sit in the system prompt. When a request matches, the agent calls load_skill and the full playbook enters the conversation, so unused skills cost almost nothing.

How a skill gets triggered

  1. The prompt lists every skill.Name plus "Use when…" description, rebuilt each model call.
  2. The model matches the request.It can pick several, e.g. a budget itinerary needs two.
  3. It calls load_skill.The playbook text comes back as a tool result in the thread.
  4. It follows the playbook.Research with tools, then answer in the skill's format.
