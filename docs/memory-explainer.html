How AskTravel remembers

AskTravel is a travel-planning ReAct agent. It runs behind Open WebUI, researches with guidebook and live-search tools, and keeps its state in Postgres. This explainer maps every piece of that state to a memory type in one framework.

CoALA

The whole explainer is organised by CoALA, Cognitive Architectures for Language Agents (Sumers et al., 2024). CoALA splits an agent's memory into one working memory (what the model sees now) and three long-term stores: episodic, semantic and procedural.

Chapter 1

Memory types

CoALA names three long-term stores, each answering a different question: what happened (episodic), what is true (semantic), and how to do things (procedural). All three feed working memory.

working memory

Working memory is the ReAct agent's context window

In CoALA, working memory is what the agent sees and reasons over right now. In a ReAct agent that is the context window sent with each model call. AskTravel rebuilds it before every call, and every step of the loop sends all of it again. Each part is filled from one of the long-term stores below.

  1. Base rulesagent/prompts.py
    1,121

    Guidelines, citations, when to save or recall memory, how earlier turns are shortened

  2. Skills indexskills/*.md frontmatter
    298

    7 skill names with their "Use when…" lines; bodies load on demand

  3. Saved facts and tripsstore · (email, memories / trips)
    676

    Every saved fact plus one line per current trip, with its status ("upcoming, in 25 days")

  4. Tool schemastool docstrings
    2,894

    13 tools; present_itinerary alone is 931

  5. Conversationcheckpointer · this thread
    11,177

    This turn in full; earlier turns as question, answer and a one-line note of tools used. Was 17,780 before M2

  6. Tool resultscheckpointer · this thread
    5,085

    This turn's results, plus loaded skills and the latest itinerary. Was 49,692 before M2: every guidebook page ever read

Semantic

Stores knowledge: facts about the user and about the world.

About the user

Stored in

Note · lecture p. 21

Parametric vs context memory

Parametric: in the model weightsContext: added to the prompt
semanticPre-trained knowledge. gpt-6-luna knows Rome has the Colosseum.Retrieved facts. Saved facts and trips, guidebook pages, flight and hotel results.
proceduralInstruction following, learned in training.Retrieved skills. The 7 playbooks and the prompt rules.
episodicNot applicable.Retrieved conversations: the current thread, plus past chats on demand via recall_conversations.

Parametric memory changes only by fine-tuning, which this POC doesn't do. Every improvement here is about what gets into context, when, and how.

Reference: LangChain · Memory overview. It uses the same three types and maps them to LangGraph: short-term (thread-scoped) memory is the checkpointer; long-term memory is the store, organised by namespace and key.

Architecture: what, when and how

Every memory design answers three questions. Here are the lecture's options, what AskTravel does after the M0–M4 roadmap, and what is still ahead.

QuestionOptions (lecture)AskTravel todayNext
Whatgets stored and retrieved? Facts (specific and general), procedures, conversation progression
  • semantic facts with provenance (which chat, when confirmed, sensitive or not); trips with stable ids; itineraries
  • procedural hand-written skills and rules
  • episodic raw chat threads, every step, plus a chat index to find them
 Expiry for trips and sensitive facts (M6); skill proposals from feedback (M7)
Whenis it triggered? Agent tools (on demand), background workers, event-driven
  • Agent tools: save_memory, save_trip_details, get_trip, recall_conversations, load_skill
  • Events: checkpoint after every step; chat index after every run; each itinerary filed under its trip; earlier turns compacted before every model call; chat deleted in Open WebUI → trigger

Howis it stored and retrieved? Filesystem, databases (retrieval), knowledge graphs

  • Filesystem: skills and guidebooks as markdown, keyword search
  • Knowledge graph: none
 pgvector in the same Postgres, only if keyword recall falls short
Chapter 3 · how

Where memory lives: filesystem vs Postgres vs MongoDB

The POC uses two of the lecture's three systems: files for what people write, Postgres for what the agent writes. A document database such as MongoDB is the obvious alternative for the agent's JSON memories.

FilesystemPostgres · usedMongoDB (NoSQL)
Data modelEvery memory is a file; folders give hierarchy for freeTables plus jsonb columns: relational and document in oneJSON documents in collections; flexible schema
How the agent reads itgrep, ls, read: the agent can manage its own filesKey lookup through LangGraph's store; SQL for peopleQueries on document fields
Search by meaningNone built inpgvector extension, same databaseAtlas Vector Search
ConsistencyWeak with many writers; no transactionsTransactions across checkpoints, store and audit tablesDocument-level atomicity; multi-document transactions available
Expiry (TTL)Manual clean-up jobsLangGraph store TTL with a sweeper; jobs for checkpointsNative TTL indexes
LangGraph supportAny custom toolsOfficial langgraph-checkpoint-postgres, which provides both the checkpointer and the storeMongoDB-maintained checkpointer and store integrations
Reviewing and auditingDiffs and pull requests in gitSQL, the inspection notebook, joins to feedbackAggregation pipelines; joins are awkward
Running itNothing to runAlready running; RDS on AWSAnother service to run and back up
Best forProcedural memory people reviewEpisodic and semantic memory at small to medium scaleVery large or fast-changing document memory, or teams already on MongoDB
proceduralFilesystem (git)Skills are reviewed like code. Stays.
episodicPostgres checkpointerSearched by keyword for recall; pgvector only if that falls short.
semantic · userPostgres storeCollection of facts and trips, with provenance; TTL next.
semantic · worldFiles todayPostgres full-text or pgvector if keyword search falls short.

MongoDB isn't needed for this POC: Postgres already holds the JSON and gives transactions, SQL for review and pgvector, without adding a second database. Open WebUI moved onto the same Postgres too (schema open_webui), so a trigger on its chat table can tell the agent when a chat is deleted. One database is what makes that possible: a trigger can't write across databases.

Chapter 4 · when · lecture p. 29

Memory patterns: what's implemented

The lecture's four architecture patterns, each set against what the POC does after the M0–M4 roadmap.

ImplementedPartlyNot yet
Pattern 1Partly

Learning procedures from experience

Recall past successful trajectories as reusable skills.

Voyager · Agent Workflow Memory · skill files
  • Skill files: 7 playbooks, loaded only when a request matches
  • Trigger eval: 9/9 cases load the right skill
  • Learning new skills from feedback and good runs (roadmap M7)
Pattern 2Implemented

Tiered memory hierarchy

Organise memory into tiers, and let the model manage its own memory with tools.

MemGPT · MemoryOS
  • Three tiers: the context window (what the model sees now), this chat's saved thread, and long-term memory (facts, trips, past chats)
  • The model moves things between tiers itself, with tools: it saves and deletes facts and trips, and fetches a trip's full plan when it needs it
  • The context window stays small: earlier turns are sent as question and answer only, without their tool results (M2)
  • Past chats are searched only when needed, with recall_conversations (M3)
Pattern 3Not yet

Reflective memory consolidation

Reflect on experiences before storing them as memory.

Reflexion · Generative Agents
  • Deliberately deferred (M5): summaries would cost a model call per turn, and the evals show no failure they would fix. Recall searches the raw chats instead; updates are checked by rules on write
Pattern 4Partly

Memory maintenance

Clean up, update and remove old memories.

Sleep-time compute · Mem0-style add / update / delete
  • Cleaned as it's written: mentioning a trip again updates it instead of creating a duplicate (M1a); likes and interests are kept as lists, and replacing a fact shows the old value (M1b)
  • Older data upgraded at startup: old trip ids re-keyed, run-on facts split, itineraries linked to their trips
  • Forgetting on request: "forget my diet" in the chat, delete everything through the API, or delete a chat in Open WebUI (M4)
  • Not yet: automatic expiry and pruning of old checkpoints (M6), and an LLM pass that resolves conflicting facts (M5)
In the hot path · todayMemory writes happen during the conversation, through a tool call or a checkpoint, and deterministic rules clean them as they're written. No extra model calls: the provider allows about 20 a minute.
In the background · today and nextToday only the chat-deletion sync runs in the background. Retention (M6) and skill proposals (M7) will too, with no latency for the user. LangChain's memory guide describes both modes.

One design choice ran through all of it: never rewrite the saved thread to save tokens. Summarising the stored history would have broken regenerate and edit in Open WebUI, so compaction changes only what the model is sent.
